    Multi-Agent DPO

    Multi-Agent Direct Preference Optimization (MADPO) trains the agents directly from preferred and rejected joint responses, without a reward model or a separate RL stage. Its loss combines all agents’ preference margins, so each policy learns from the team’s outcome.

    The training flow is: task items → preference pairs → joint preference loss → policy updates. MARLHF uses the same pairs to fit a joint reward model first and then trains the policies with RL.

    The diagram uses the same task item and preference pairs as the MARLHF figure; here the agents’ margins enter one joint loss directly.

    Preference Pairs#

    Each agent \( i\in\mathcal{I}=\{1,\ldots,n\} \) samples \( a_{i,t}\sim\pi_{\theta_i}(\cdot\mid h_{i,t}) \) from its local history; the responses form the joint action \( \mathbf{a}_t=\{a_{1,t},\ldots,a_{n,t}\} \) with joint history \( \mathbf{h}_t \). Only a single turn is currently supported (horizon \( H=1 \)), so \( h_{i,0} \) is agent \( i \)’s prompt and \( \mathbf{a}_0 \) is the joint response.

    For each task item in train_dataset, every agent samples preference_num_candidates responses from its formatted prompt. Responses with the same candidate index form a joint response and share one reward from reward_func (after the optional reward_processor). For two joint responses with different rewards, the response with the higher reward is the winner \( w \) and the other the loser \( l \); ties are discarded. Each pair \( (\mathbf{h}_H^{w},\mathbf{h}_H^{l}) \) contains the two joint histories for one task.

    The base trainer collects the pairs once and reuses them for num_train_epochs; pair_selection and preference_pairs_per_sample determine which pairs are retained for each task.

    MADPO currently requires num_turns=1 and joint_mode="aligned". pair_selection="all" requires preference_pairs_per_sample=None. If no task yields a non-tied pair, training returns without updating the policies.

    Joint Preference Objective#

    Each agent’s margin is the difference between its log-probabilities for the winning and losing responses. The joint margin sums these differences across agents:

    \[ \Delta_{\theta_i}=\sum_{t=0}^{H-1}\Big(\log\pi_{\theta_i}(a_{i,t}^{w}\mid h_{i,t}^{w})-\log\pi_{\theta_i}(a_{i,t}^{l}\mid h_{i,t}^{l})\Big), \qquad \Delta_{\boldsymbol{\theta}}=\sum_{i\in\mathcal{I}}\Delta_{\theta_i}. \]

    MADPO minimizes

    \[ \mathcal{L}_{\mathrm{MADPO}}(\boldsymbol{\theta}) =-\mathbb{E}_{(\mathbf{h}_H^{w},\mathbf{h}_H^{l})\sim\mathcal{B}} \Big[\log\sigma\big(\eta\,\Delta_{\boldsymbol{\theta}}\big)\Big], \]

    where \( \sigma \) is the sigmoid function, \( \eta>0 \) is dpo_beta (default 0.1), and \( \mathcal{B} \) is the set of training pairs. The task reward determines only the ordering within each pair; the loss itself uses the policies’ log-probabilities.

    The gradient for agent \( i \) is

    \[ \nabla_{\theta_i}\mathcal{L}_{\mathrm{MADPO}}(\boldsymbol{\theta}) =-\eta\,\mathbb{E}_{\mathcal{B}} \Big[\sigma\big(-\eta\,\Delta_{\boldsymbol{\theta}}\big)\,\nabla_{\theta_i}\Delta_{\theta_i}\Big]. \]

    The weight \( \sigma(-\eta\,\Delta_{\boldsymbol{\theta}}) \) depends on the team’s joint margin, while the gradient flows only through agent \( i \)’s own margin. In each batch, the trainer computes all margins once without gradients, then updates each agent with its own differentiable margin plus the others’ detached margins.

    Reference-Free Implementation#

    Equation 6 of the MAPL paper replaces \( \log\pi_{\theta_i} \) in \( \Delta_{\theta_i} \) with the log-ratio \( \log(\pi_{\theta_i}/\pi_{\mathrm{ref},i}) \) against a frozen reference policy. CoMLRL implements the reference-free form above: the inherited reference_kl_enabled, reference_kl_coef, and reference_devices settings do not add reference terms to the MADPO loss.

    The decentralized scorer excludes the last completion token after trimming padding, so each agent’s margin omits that token’s log-probability. The centralized scorer covers the full joint completion.

    Configuration#

    Users can import MADPOConfig and MADPOTrainer from comlrl.trainers.preference.

    MADPOConfig Parameters
    • num_agents: Number of agents in decentralized mode, or task roles in centralized mode
    • collaboration_mode: "decentralized" (default) or "centralized"
    • num_train_epochs: Optimization epochs over the collected preference pairs
    • agent_learning_rate: Policy learning rate
    • preference_num_candidates: Candidates sampled per task and actor; at least 2
    • preference_pairs_per_sample: Maximum pairs retained per task, or None for no limit
    • pair_selection: "reward_gap" selects pairs with the largest reward gaps, "random" selects a random subset, and "all" retains every non-tied pair
    • dpo_beta: Positive coefficient on the joint margin
    • train_batch_size: Preference pairs per update; defaults to rollout_buffer_size
    • max_new_tokens, temperature, top_p, top_k: Candidate generation settings
    • parallel_training, agent_devices: Policy execution mode and device placement
    • eval_interval, eval_num_samples, eval_batch_size: Evaluation schedule and sample sizes; MADPO counts eval_interval in preference updates
    • logging_steps: Training logging interval
    MADPOTrainer Parameters
    • agent_model or agents: Model identifier for homogeneous agents, or a list of model identifiers or instances
    • num_agents: Number of agents or task roles; must match args.num_agents
    • tokenizer: One tokenizer, or one per actor
    • train_dataset: Task items from which preference candidates are generated
    • eval_dataset: Optional evaluation dataset
    • reward_func: Required callable returning one shared reward per aligned joint response
    • reward_processor: Optional post-processing of task rewards
    • formatters: One prompt formatter shared by all roles, or a list of role-specific formatters
    • args: MADPOConfig instance
    • model_config: Optional model loading configuration
    • wandb_config: Optional Weights & Biases configuration
    • eval_logger, eval_aggregator: Optional evaluation metrics hooks, as in MAGRPOTrainer
    • centralized_comparator_adapter: Prompt builder and response parser for centralized actors or comparators

    Evaluation samples responses from the current policies and scores them with the task reward. The training metrics turn_1/reward_mean and turn_1/expected_return instead average the candidate rewards recorded when the pairs were collected; they do not reflect the updated policies.

    Collaboration and Iterative Training#

    Decentralized MADPO trains one policy per agent with the summed margin \( \Delta_{\boldsymbol{\theta}} \). With collaboration_mode="centralized", one actor \( \boldsymbol{\pi}_{\boldsymbol{\theta}}(\mathbf{a}_t\mid\mathbf{h}_t) \) generates the complete joint response, and \( \Delta_{\boldsymbol{\theta}} \) is that actor’s margin on the joint text. num_agents must equal the number of task roles, and the configuration requires one actor and tokenizer. The joint text is retained for preference training and parsed into role responses only for task rewards and evaluation. Training Framework describes the layouts and adapter interface.

    MADPOIterTrainer repeats data collection and training. Iteration \( \nu \) pairs each new current-policy sample with the comparator sample at the same candidate index (either side can win), then applies the MADPO updates to the selected pairs \( \mathcal{B}^{(\nu)} \). An iteration is not a dialog turn, so the single-turn, aligned-response restriction still applies.

    Training Framework describes the iterative configuration, the comparator, and the replay buffer that selects \( \mathcal{B}^{(\nu)} \).
